# Stocky replacement: reorder and purchase-order drafts

Built by Daniil Maximkin (taskfordaniel.com).

A small offline Node 22 demo for a merchant's purchasing rules:
90 days of synthetic Shopify-style orders + inventory snapshot -> sales
velocity -> low-stock signal -> supplier PO (CSV + JSON) -> supplier email
draft -> explicit local approval receipt.

All store, supplier and variant records are invented. The only shop is
`demo-store.example`; all supplier addresses end in `.example`. Zero runtime
or development dependencies. No network requests, emails or stock changes.

## Run

```sh
nvm use                  # or use an already installed Node 22
npm test
mkdir -p out
npm run demo             # creates out/demo; refuses if it already exists
```

No install or credentials are needed. Use a fresh directory for another run:

```sh
node src/cli.mjs generate --input fixtures --out out/review-002
```

The output directory's parent must exist. Generation validates the complete
input before creating it. An I/O failure can leave a partial directory;
`run.json` is written last and is the completion marker. Existing directories
and approval files are never overwritten.

The checked-in [examples/](examples/) are actual deterministic output from
the fixtures, not hand-written sample POs. Tests compare generated bytes to
these examples and check every SHA-256 in the run manifest.

The CLI prints the run manifest, including these final counters:

```text
  "stockWrites": 0,
  "emailsSent": 0,
  "networkRequests": 0
}
```

## Rules and forecast maths

The fixture snapshot is `2026-10-01T00:00:00Z`. The 90 complete UTC days are
`[2026-07-03T00:00:00Z, 2026-10-01T00:00:00Z)`. There are 90 daily orders plus
four exclusion examples: cancelled, test, before-window and window-end.
The first tea line also demonstrates a partial refund.

For each variant:

1. Start exposure at the later of the window start and `launchedAt`.
2. Subtract the union of known full-day stockout intervals, clipped to that
   exposure. Intervals are `[from, to)`. Overlaps are counted only once.
3. Sum `currentQuantity` from non-test, non-cancelled orders in the window.
4. `velocity = retained units / selling days` (units per day).
5. `reorder point = ceil(units * lead days / selling days) + safety units`.
6. `target = ceil(units * (lead days + review days) / selling days) + safety units`.
7. `position = available + confirmed incoming`.
8. If `position <= reorder point`, `raw quantity = max(0, target - position)`;
   otherwise propose zero. Negative available is treated as backorders.
9. For positive demand only, `quantity = ceil(max(raw quantity, line MOQ) /
   pack size) * pack size`. A line MOQ never creates demand by itself.

Integer demand is divided last to avoid floating-point over-ordering at exact
boundaries. The displayed velocity retains full precision. Unsafe integer
arithmetic is rejected. Costs and totals are integers in USD cents.

Example: mug sells 180 units / 90 days = 2/day. Lead time 10 days, safety 6,
review period 14: reorder point 26, target 54. Available 8 + incoming 6 gives
position 14; shortage 40 rounds to 42 in packs of 6.

Zero sales means zero velocity; a configured safety-stock floor can still
generate a proposal. A product with no selling days gets `manual_review`
with null velocity and no invented quantity. New products use their shorter
exposure and are flagged; fewer than 14 selling days raises `limited_history`.
Sales during a declared stockout or before launch are rejected as conflicting
data, rather than used to inflate velocity.

Suggested lines are grouped by supplier. Line pack sizes and MOQs affect
quantities; aggregate supplier unit/value minimums affect eligibility. A
shortfall blocks approval, without automatically padding the purchase.

## Human review and local approval

1. Read `forecast.csv` and `forecast.json` for demand, stock and warnings.
2. Check a supplier's PO JSON/CSV and email draft. Verify unit costs, incoming
   arrival dates, stockouts, launch dates, pack sizes and supplier terms.
3. Revise fixture rules or stock and generate a fresh run if changes are
   needed. Recheck the new output. Defer a supplier PO if its minimum is unmet.
4. Obtain the SHA-256 of the reviewed JSON from `run.json` or compute it:

```sh
shasum -a 256 out/demo/PO-2026-10-01-demo-supplier-home.json
```

5. After reviewing, pass that digest explicitly (replace the placeholder):

```sh
node src/cli.mjs approve \
  --po out/demo/PO-2026-10-01-demo-supplier-home.json \
  --sha256 REVIEWED_64_CHARACTER_SHA256 \
  --reviewer demo-operator \
  --out out/demo/home-approval.json
```

The separate receipt binds `approved_locally` to the exact PO bytes, reviewer
and time. A changed digest, invalid totals, invalid packs or supplier minimum
shortfall is refused. The email remains a draft file. There is no send command.

`PO-<date>-<supplier>.{csv,json,email.txt}`, and `run.json` with input digest,
exclusions, PO totals and output digests. JSON is the authoritative artifact;
CSV text cells are protected against spreadsheet formula interpretation.

## Background

This offline demo illustrates the purchasing workflow described in
[Stocky replacement operations apps](https://taskfordaniel.com/use-cases/stocky-replacement-ops-apps/)
and [rebuilding reorders](https://taskfordaniel.com/guides/stocky-gone-rebuilding-reorders/).

## Limits

- Not an installed Shopify app or live dev-store integration.
- Simple mean sales velocity, not a statistical or seasonal forecast. No
  promotions, trend weights, service-level model or probabilistic safety stock.
- One replenishment location, USD, integer units and fixed lead/review times.
  Safety stock and supplier rules are configured, not learned from Stocky.
- Current quantity is a net-sales proxy. Monetary refunds without removed
  units, fulfillment demand and return/restock timing need an explicit policy.
- Stockout adjustment assumes stable demand and full-day unavailability;
  it cannot recover lost orders or infer historical stock from today's level.
- Incoming stock is assumed timely and confirmed. There is no arrival-date
  model, open-PO database, cross-run reservation or live stock recheck.
- All POs stay drafts. Local approval is unauthenticated and receipts are
  ordinary editable files, not a tamper-proof audit log or production approval
  system. Their digest binds content; it does not verify the approver's identity.
- No supplier sending, confirmations, receiving, stock postings, native PO
  creation, embedded UI, scheduler or reconciliation with spreadsheets.
- Not tested against real or dev-store data. GraphQL examples are documented
  only. See [Shopify integration](docs/shopify-integration.md) for permissions,
  nested pagination, historical availability and the future approval boundary.
- Fresh run directories prevent overwrites, but two runs can propose the same
  purchase. A production app must reserve and reconcile approved open POs.
